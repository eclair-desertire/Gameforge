# Build — реализация задачи с проверкой в движке

## 0. Подготовка

1. Возьми задачу: ID из запроса или первая `[ ]` в текущем milestone `backlog.md`. Отметь `[~]`.
2. Прочитай engine-скилл проекта (**gameforge:engine-unity / engine-godot / engine-unreal**) — там команды компиляции, тестов, запуска.
3. Если в задаче указан узкий скилл (`скилл: unity:ui` и т.п.) — загрузи его.
4. Прочитай затронутый код и соответствующий раздел `gdd.md`.

## 1. Цикл

```
изменить код/данные
  → компиляция (ошибок 0, новые warning — разобрать)
  → самый дешёвый тест, который доказывает изменение (unit / EditMode / headless)
  → запуск игры и проверка поведения (playmode / run_project / PIE)
  → консоль без исключений
  → критерий «Готово, когда» выполнен?
```

Повторяй, пока критерий не выполнен. **Не объявляй задачу готовой без шага «запуск и проверка»**, если в задаче он указан. Если проверить нельзя (редактор не запущен, нет устройства) — так и скажи, отметь `[~]` с пометкой «не проверено в игре».

## 2. Правила для движков

- **Сцены, префабы, .uasset, .tscn при открытом редакторе меняем через редактор** (Unity: `unity command`/`script eval`; Godot: MCP или скрипты `@tool`/`--script`; Unreal: Python в редакторе / MCP), а не правкой YAML/бинарей руками.
- Unity: каждый новый файл в `Assets/` получает `.meta` от редактора — не создавай `.meta` руками, дай редактору импортировать (`unity recompile` / refresh).
- Godot: не ломай `uid://` — после переноса файлов прогоняй обновление UID (MCP `update_project_uids` или открытие проекта редактором).
- Баланс и числа — в данные (ScriptableObject / Resource / DataTable), не в константы кода.
- Новый скрипт → минимум один тест, если логика не чисто визуальная.

## 3. Завершение

1. `backlog.md`: `[x]`, ссылка на коммит, если есть.
2. GDD расходится с реализацией? Обнови GDD (+ версия и «История изменений») или верни реализацию.
3. Запись в конец `.gameforge/history.md` (сделано / решено / проверено / дальше); новые термины и решения — в `context.md` (см. gameforge:project-memory).
4. Предложи коммит (не коммить без просьбы пользователя).
5. `state.md` → «Следующий шаг»: следующая задача или gameforge:playtest, если закрыт milestone.

Для крупной задачи отдай реализацию агенту `gameplay-programmer` с ID задачи и путём к проекту; проверку результата — `qa-playtester`.
